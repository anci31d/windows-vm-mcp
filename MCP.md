# Общий доступ к Windows VM через MCP

Сервер `bin/windows-vm-mcp` работает локально по MCP stdio. Каждый клиент запускает собственный процесс сервера; они используют общую блокировку и файл аренды в `.mcp-state`. Виртуальная машина одна, и доступ к ней предоставляется по очереди. Windows ISO и VirtIO ISO ещё не готовы; установка и проверка Windows описаны в `CONTINUE.md`.

## Подключение

Зависимость MCP установлена в `.venv` внутри workspace. Для восстановления окружения при необходимости:

```bash
UV_CACHE_DIR="$PWD/assistant-work/uv-cache" uv venv .venv
UV_CACHE_DIR="$PWD/assistant-work/uv-cache" uv pip install --python .venv/bin/python -r requirements.txt
```

Для Codex команду ниже выполняет пользователь: она изменяет общую конфигурацию Codex за пределами этого workspace. Синтаксис проверен по `codex mcp add --help`:

```bash
codex mcp add windows-ctf -- /absolute/path/to/windows-vm-mcp/bin/windows-vm-mcp
```

Перезапустите клиент или его MCP-подключение, затем проверьте наличие инструментов `vm_status` и `acquire_vm`. Для другого клиента зарегистрируйте локальный stdio-сервер с абсолютным путём к `bin/windows-vm-mcp` и без аргументов. Например, в клиентах, поддерживающих JSON-конфигурацию `mcpServers`, запись может выглядеть так:

```json
{
  "mcpServers": {
    "windows-ctf": {
      "command": "/absolute/path/to/windows-vm-mcp/bin/windows-vm-mcp",
      "args": []
    }
  }
}
```

Конкретное место конфигурации и необходимость перезапуска определяются клиентом. Сервер должен выполняться под тем же пользователем и иметь доступ на чтение/запись к этому каталогу, QEMU-сокетам и диску VM, а для запуска VM — к KVM и необходимым системным ресурсам. Для передачи файлов он также должен иметь права на указанные пути проектов. MCP не выдаёт эти права и не монтирует каталоги: в песочнице другого клиента может потребоваться настроить разрешения или запускать MCP-сервер вне неё. Способ настройки зависит от клиента и не проверен для всех клиентов.

## Использование агентом

1. Вызвать `vm_status`, затем `acquire_vm` с понятным именем задачи. Сохранить полученный токен приватно: он нужен для всех изменяющих операций. Не включать токен в отчёты и журналы задачи.
2. Передать токен в `start_vm`; дождаться готовности `guest_ping`. При необходимости пользователь может подключиться к уже работающей VM через `bin/winvm gui`.
3. Передавать файлы вызовами `put_file` и `get_file` с **абсолютными** путями на хосте и путями Windows в госте. `put_file` перезаписывает гостевой файл. `get_file` по умолчанию не перезаписывает файл хоста; для этого требуется `overwrite=true`. Операция записи в гостя при сбое может оставить частичный файл.
4. Запускать программу через `execute`: указать полный Windows-путь `program` и список `arguments`. Это прямой запуск, без автоматического преобразования строки в команду оболочки. Вывод возвращается в UTF-8 с заменой некорректных байтов и в Base64 для точного восстановления; возможное усечение отмечается полями гостевого агента.
5. При таймауте процесс **не завершается**. VM остаётся занятой; проверяйте `execution_status`, пока процесс не завершится. Если связь потеряна во время запуска и PID неизвестен, выясните состояние через GUI. `recover_vm_lease(acknowledge_risk=true)` принудительно снимает аренду, но **не останавливает процесс**; использовать только после проверки, что совместная работа безопасна.
6. По завершении вызвать `release_vm`. Для выключения до освобождения аренды использовать `stop_vm` и дождаться остановки, проверяя `vm_status`. Отключение MCP-клиента не освобождает аренду автоматически.

Аренда действует между экземплярами этого MCP-сервера. Прямые вызовы `bin/winvm`, `bin/win-agent`, QEMU или доступ к гостевому сокету её обходят: не используйте их параллельно с занятой VM. Все локальные процессы с правами текущего пользователя могут самостоятельно вызвать восстановление аренды или получить доступ к VM; MCP не является границей безопасности между такими процессами. Каталог VM ограничен правами `700`, и файл состояния аренды содержит хеш токена, а не сам токен.

Windows и программы в ней не проверены. QEMU Guest Agent запускает команды в контексте своей службы, который отличается от интерактивного рабочего стола. Для изоляции повторных заданий используйте проверенную резервную копию выключенной VM вместе с EFI и TPM; восстановление состояния в MCP не автоматизировано. Вывод гостя и файлы CTF рассматривайте как недоверенные данные.

## Проверка

```bash
.venv/bin/python -m unittest discover -s tests -v
```

Тест запускает отдельные процессы MCP и имитирует QEMU Guest Agent внутри workspace. Он не запускает Windows и не подтверждает доступность KVM, SPICE, системных прав или работу реального гостевого агента.
